Long-form video storage

Confirmed design for uploading tennis-match videos from an iPhone Photos library, displaying transfer progress, resuming interrupted uploads, storing originals, and returning both a storage path and an unlisted playback URL.

Confirmed decisions

Input

iOS Photos library; MOV or MP4 containing H.264 or HEVC video.

Limits

Maximum duration: 3 hours. Maximum object size: 20 GB.

Upload behavior

Multipart transfer with byte-based progress and resume support for 24 hours.

Storage

Amazon S3 in a US region. The exact region is selected with backend hosting.

Playback

Unlisted public CloudFront URL. Videos do not appear in public search or listings.

Retention

Originals remain indefinitely until their owner explicitly deletes them.

Architecture

Large video bytes never pass through the Python API. The API controls and records the upload; the iPhone transfers each part directly to S3.

Successful upload flow

  1. Select and validateThe app reads the selected Photos asset's name, byte size, duration, container, and codec. It rejects files above 20 GB, longer than 3 hours, or outside the accepted formats.
  2. Create upload sessionThe app sends file metadata to the Python API. The API allocates an opaque video identifier, a non-guessable object key, and an S3 multipart upload.
  3. Upload parts directlyThe API supplies time-limited upload URLs. The app sends chunks to S3 and records each completed part identifier locally.
  4. Display transfer progressProgress equals uploaded bytes divided by total file bytes. It represents transfer only—not validation or later video analysis.
  5. Complete atomicallyThe app submits the completed-part list to the API. The API asks S3 to assemble the object and records the upload as complete.
  6. Return referencesThe response contains the durable storage path and a separate CloudFront playback URL.

Resume and failure handling

pending→uploading→paused→uploading→completing→ready

The app persists the video identifier, S3 upload identifier, object key, file fingerprint, part size, and completed-part records. After network loss, app termination, or device restart, it reconciles completed parts with the API and uploads only missing parts.

Incomplete sessions expire 24 hours after creation. S3 lifecycle cleanup aborts expired multipart uploads so abandoned parts do not accumulate storage charges. If the session expired, the app must create a new upload and begin again.

Photos availability: resuming requires the original Photos asset to remain available and unchanged on the device. If it was deleted or changed, the session cannot safely continue.

Names and wire formats are intentionally deferred. These are the required operations, not final endpoint definitions.

Deletion behavior

  1. Authorize ownershipThe service confirms that the requesting user owns the video. Authentication design itself remains out of scope.
  2. Disable application accessThe metadata record becomes unavailable to normal reads so the app stops presenting it.
  3. Delete the S3 objectThe stored original is permanently removed.
  4. Invalidate CloudFrontThe unlisted playback path is purged from edge caches. Propagation takes several seconds and cannot recall a download already in progress.

Security and scope boundaries

Storage permissions

The S3 bucket blocks arbitrary public writes. The app receives narrowly scoped, expiring upload URLs only for the active object and part.

Unlisted is not private

Anyone who obtains the playback URL can watch the video. Random object identifiers reduce guessing but do not provide access control.

Metadata database

PostgreSQL on Amazon RDS is recommended. Schema, sizing, availability, and deployment are deferred.

Out of scope for this design

  • User authentication design
  • Video transcoding, thumbnails, analysis, or downstream processing
  • Database schema and deployment
  • Exact Python framework and endpoint naming
  • Infrastructure provisioning and application implementation
